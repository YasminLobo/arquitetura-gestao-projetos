Presentation Domain Data Layering: separando tela, negócio e dados

Como organizar o código em três camadas claras e por que sistemas maiores devem dividir seus módulos principais por área de negócio antes das camadas.

Artigo original (Martin Fowler) ↗ ← Voltar ao início
Parte 1

Resumo da ideia central

Martin Fowler apresenta uma das formas mais importantes de organizar o código de um sistema: separar as responsabilidades em três camadas — Presentation (Apresentação), que cuida das telas e da interação com o usuário; Domain (Domínio), que concentra as regras e cálculos do negócio; e Data Source (Dados), que faz a comunicação com o banco de dados e sistemas externos.

Separar essas três partes evita que comandos de banco de dados e regras de cálculo fiquem misturados dentro do código das telas. Com isso, fica muito mais simples testar as regras do sistema, alterar consultas no banco sem quebrar a interface ou criar um aplicativo mobile reaproveitando a mesma lógica.

Um ponto essencial destacado por Fowler é que essa divisão em 3 camadas só deve ficar no nível principal quando o programa é pequeno. Quando o sistema cresce, o projeto deve ser dividido primeiro por módulos de negócio (como Preços, Pedidos e Clientes), e cada módulo usa as três camadas por dentro.

Parte 2

Vantagens e desvantagens

Vantagens
  • + Proteção das regras de negócio: Alterar o layout de uma tela ou mudar uma tabela no banco não afeta a lógica principal do sistema.
  • + Facilidade para criar testes: É possível testar os cálculos e validações rapidamente sem precisar abrir telas ou subir banco de dados.
  • + Reaproveitamento de código: A mesma camada de negócio pode atender tanto o site web quanto um aplicativo mobile.
Desvantagens
  • − Mais passos para tarefas simples: Incluir um campo novo em um cadastro básico exige mexer em arquivos nas três camadas.
  • − Dificuldade de navegação em sistemas grandes: Se o projeto inteiro tiver apenas 3 pastas gigantes, fica difícil achar tudo que pertence a uma mesma funcionalidade.
  • − Risco de colocar regra no lugar errado: Sem revisão de código, a equipe pode acabar colocando regras de negócio direto na tela por pressa.
Parte 3

Impacto na gestão do projeto

Prazo Ritmo constante

Garante que o projeto não fique cada vez mais lento com o passar dos meses, pois mudanças em uma camada não causam efeito dominó inesperado nas outras.

Custo Menor manutenção

Reduz o custo de manutenção e correção de bugs, além de economizar horas de retrabalho caso o projeto precise mudar a interface visual ou o banco de dados.

Equipe Boa divisão

Facilita a entrada de novos membros porque a estrutura do projeto é clara. Também permite que pessoas com foco em interface e pessoas focadas em dados trabalhem em paralelo.

Riscos Menor risco de bugs

Diminui muito o risco de erros nas regras principais do negócio, já que a camada de domínio fica isolada e pode ser testada automaticamente com facilidade.
